# Display service notes

Measured SkyLight/WindowServer/hardware behaviour behind `Crisp/Services`' display-toggle, mirror, virtual-display and resolution code, for anyone changing it; read the relevant heading before touching that code. See docs/ddc-notes.md for DDC/CI specifics, not repeated here.

## PhysicalDisplayToggleService

Toggles a physical display in and out of the layout with the private SkyLight call `SLSConfigureDisplayEnabled`, the way BetterDisplay's Disconnect Display works; unlike VirtualDisplayService this never creates or destroys a display object, it only flips an existing one's enabled bit. Supported on Apple Silicon only (`isSupported`); on Intel the API does not perform a true disconnect. A disabled display drops out of `CGGetOnlineDisplayList`/`CGGetActiveDisplayList` but still enumerates via `SLSGetDisplayList`, so reconnect re-finds it there; DisplayManager also loses it from `displays`, so the service keeps its own `disconnected` snapshot for the Reconnect row. `setEnabled` holds `DDCService.shared.hold()` around the whole SkyLight transaction: WindowServer's enable can wait behind an in-flight DDC I2C read on the DCP and freeze the whole machine with it, not just Crisp (issue #33: a 6 s volume read produced a 6 s system freeze on reconnect, three times in a row). `CGCompleteDisplayConfiguration` runs with `.permanently` (matching Lunar BlackOut, screen_tune and BetterDisplay) inside a 10 s timeout wrapper that can only stop waiting, never cancel the underlying WindowServer call, so a reported timeout is not proof the change did not happen; issue #33 saw WindowServer hold one commit for 29.5 s.

## phantomAwareActiveDisplayCount

The blackout rescue's active-display count: `physicalActiveDisplayCount` with the #112 phantoms removed. Only `restoreIfNoActiveDisplay` reads it; a wrong answer here can only make the rescue fire (re-enabling a display Crisp itself turned off), never hide a row or refuse a remembered disconnect. The shape filter in `viewableActiveDisplays` already catches an entry with nothing behind it (vendor/model 0, or the four-character 'unkn'/'virt' placeholder macOS spawns once the last real display is gone, which cannot fit in EDID's 16-bit fields), but misses the #112 case: after an undock while asleep, WindowServer re-enumerates the absent externals at full wake with their EDID identities intact, so they read active, 16-bit and real until the dock goes back in (measured 104 s dark, rescue standing down at count 2). The fix asks the ports: cap the external count at what the DisplayPort/Thunderbolt transport nodes' hot-plug detect or sink count say is live (`liveDisplayPortCount`). Presence alone under-caps (an empty HDMI port keeps its transport node), so entries beyond the cap are further filtered by whether CoreDisplay still reports a product name (`hasProductName`): a phantom has none, a lit DisplayLink display (which carries no port node of its own) does. This uses the name rather than `kCGDisplayIsVirtualDevice`, because that flag reads 1 on phantoms and also on any real monitor mid re-enumeration (measured through a display sleep: virtual 0 to 1, transport 1 to 0, product name to empty, all back at wake). Two residuals are accepted rather than patched: a phantom that happens to carry a name is counted and the rescue stands down anyway (true without this rule too), and a DisplayLink-only desk in display sleep reads 0 for the length of the sleep and could fire the rescue; field reports decide if either needs more. The info-dictionary lookup costs 2.5 to 8 ms per display, so it only runs when the port count reads lower than the externals lit.

## liveDisplayPortCount

Counts DisplayPort/Thunderbolt transport nodes with hot-plug detect asserted or a sink counted on them; returns nil, not 0, when the machine exposes no such nodes at all, since that means the signal is unavailable rather than that nothing is plugged in (capping on 0 there would black out an unseen desk shape). Either signal (hpd or sink) alone is enough, because each drops out on its own for a few hundred ms around a transition while the other holds: measured `hpd=Low sink=1` right after an enable and `hpd=High sink=0` during a wake, with hpd alone capping a real display away in both cases. An empty port reads `hpd=Unknown sink=0` (a built-in HDMI port) or `hpd=Low sink=0` (an emptied dock port), and in the phantom state the whole node is gone, so the pair reads zero there too, which is the right answer.

## restoreStates

macOS keeps a saved mode/rotation/HDR arrangement per set of attached displays and re-applies it the instant the set changes, so disabling one display can visibly move the others to whatever they last ran at in the smaller set (issue #108: a 1440p 165 Hz panel dropped to 1080p 60 Hz and the built-in changed scale). This is WindowServer's own behaviour and cannot be prevented from inside the same transaction, so `disconnect()` and the remembered-disconnect re-apply (`reapplyRemembered`) capture the other displays' mode, rotation and HDR beforehand (`currentStates`) and restore whichever ones moved in a second transaction once the new arrangement has landed (`restoreStates`), polling rather than sleeping so the user-visible flip stays as short as possible. Mode is not the only thing an arrangement carries: a portrait panel came back at 0 degrees and a monitor switched into HDR because the fallback arrangement had been left that way, so both are captured and replayed too. The reapply path's snapshot (`baselineModes`/`pendingPassModes`) must be taken on the refresh BEFORE the remembered display comes back online, not live inside the reapply: measured rather than reasoned (issue #101), the enable that brings a remembered display back has already moved the others to WindowServer's stored arrangement for the larger set before the reapply's own restore runs, so a live snapshot would capture the moved state and pin it right back, undoing WindowServer's own correction (observed: the built-in cycled 1352x878 to 1512x982 to 1352x878 to 1512x982 again). One restore snapshot is taken per reconcile pass, not per record, because two records each taking their own snapshot landed the same restore twice, 19 ms apart.

## softReconnect

Disables then re-enables a display's framebuffer to force macOS to re-read a freshly written HiDPI EDID override and re-enumerate its modes, which is what lets smooth-scaling/HiDPI injection take effect without a physical unplug: `IOServiceRequestProbe` and `SLSDetectDisplays` are both verified no-ops for this, only the off-to-on framebuffer toggle re-reads the override (verified live: an external's mode count went 149 to 113 when the override was removed and 113 to 149 when restored, each time via this toggle). The screen blanks about 1 s. Unlike `disconnect()` this leaves the `disconnected` set untouched (it is a re-enumeration blip, not a user-visible disconnect) and will blink even the sole active display, since refusing would leave the override a silent no-op until the next reboot or replug (issue #58). On a portable, disabling the sole active display triggers Clamshell Sleep immediately, even under a `PreventSystemSleep` assertion (verified live), so a throwaway virtual display is held for the blink's duration to keep the display count above zero, which does prevent it (`makeBlinkSleepGuard`; battery presence is used as the lid-independent laptop test, since the built-in can vanish from the display list entirely while the lid is closed). The re-enable is fired without awaiting: `CGCompleteDisplayConfiguration` can block up to about 10 s past the display's actual return while the link retrains after an override rebuild, and its own success/failure result is untrustworthy in both directions, so only enumeration (`verifyBackOnline`) counts. The verify window is 4 s to outlast a display link handshake (2 to 4 s); re-issuing enable mid-handshake restarts the link and blinks it again. Re-enumeration can renumber every mode ID (observed: the same timing went 130 to 683) and can land on macOS's default mode instead of the one the user had (observed on a 180 Hz panel), so the pre-blink mode is captured by attributes, not ID, before the sleep guard exists (the guard's own arrival alone knocked one panel from 165 Hz to 144 Hz, observed live) and re-applied by matching the fresh mode list once the display is back. Two safety nets back up a stranded blink: a dead-man UserDefaults marker, cleared only once the display verifiably returns, recovered by `recoverStrandedSoftReconnect` at the next refresh or launch if the app dies mid-toggle; and a full sweep of unintentionally-disabled displays (`reenableUnintentionallyDisabled`) if every re-enable retry fails outright.

## reconcile

A physical disconnect is stored by UUID and, without this, only lasted until the display next showed up: a monitor kept switched off but still cabled enumerates as ordinary at every boot, so the same disconnect had to be redone by hand every time (issue #93). `reconcile` re-applies a remembered disconnect once its display resurfaces, but only when doing so is safe (`wouldLeaveNoActiveDisplay` still applies, and `restoreIfNoActiveDisplay` is the backstop underneath), and a display still lit after the attempt drops its record, so the list never claims a display is disconnected while the user is looking at it. That invariant costs one case on purpose: booting with the remembered display as the only screen attached forgets the record for that boot (the case #93 opened with), because honouring it would boot to a black machine; a list that can misname what is on screen is judged the worse failure. `reapplyRemembered` decides a record's fate by enumeration, never by the disable transaction's own result, for the same lying-success reasons as the rest of this file: it waits up to 4 s (a display link handshake runs 2 to 4 s) before believing the display is still lit, then a further 2 s before actually dropping the record, and never drops it at all after a reported timeout, since issue #33 has WindowServer holding a commit for 29.5 s and the timeout wrapper cannot tell whether that commit will still land.

## restoreIfNoActiveDisplay

The blackout rescue: a physical unplug bypasses `disconnect()`'s last-screen guard entirely (disable the built-in via Crisp, then pull the external cable, and zero active displays remain with macOS not re-enabling the disabled one on its own), so this re-enables a still-attached disconnected display, built-in first, whenever nothing viewable is left. Grew a layer per desk shape (issues #91, #99, #106, #117, #112) and is written down here as a contract: it reads CoreGraphics and, for the undock case, the port transport nodes (nothing else in Crisp reads the ports); a display not on a port (the built-in, or a DisplayLink display that keeps its product name) is never doubted; it accepts about three seconds of dark; a desk shape it does not cover waits for a field report, not a new predicate. Before acting it re-polls `phantomAwareActiveDisplayCount` (up to 10 times, 100 ms apart) rather than trusting one sample, because the count is this process's own cached copy of the display configuration, refreshed only by reconfiguration-callback delivery: on issue #117 the external was back in the active list for 284 ms, visible to other processes, while this read still returned 0 and the callback arrived 37 ms after the decision (margins measured three times on two builds: 37 ms, 37 ms, 158 ms). The poll is bounded rather than a standing watch, because the same count during a display sleep is not reliable either (measured staying at 1 through a 35 s sleep with Crisp running, and reading 0 for almost three minutes with Crisp quit); what keeps the rescue clear of a merely-asleep desk is that it only runs from reconfiguration callbacks, which do not arrive while the displays are down. Once acting, records that fail to re-resolve fall back to their last-known ID rather than being dropped, since in the placeholder-display state `SLSGetDisplayList` shrinks to just the placeholder and `SLSConfigureDisplayEnabled` still honors a stale ID for attached hardware (detached hardware fails at `CGCompleteDisplayConfiguration` and the loop moves on); the built-in is tried first, using the `isBuiltin` flag captured at disconnect time, since a live query is unreliable on the stale IDs in this state.

## MirroredModeService

Delivers true HiDPI past WindowServer's scaled-backing cap (issue #65): on 5K2K ultrawides macOS refuses scaled backings wider than about 6720 px, so looks-like sizes between the smooth-scaling ladder's top (about 3360 wide) and native never enumerate as HiDPI on the physical display. The service creates a hidden virtual display whose framebuffer is rendered rather than scanned out (the cap does not apply there), drives it to the wanted looks-like HiDPI mode, and hardware-mirrors the physical panel onto it, letting the scanout engine downscale. `createMirrorVirtual` must declare both the 2x backing AND the half-size pixel mode for every beyond-cap stop: a backing-only declaration gets WindowServer to mint an enumerable looks-like twin, but that twin fails to ever apply (`CGConfigureDisplayWithDisplayMode` fails every attempt, verified on a 5K2K panel); only the declared pair yields a twin that can actually become current. Only one refresh rate is declared, matching the panel's own, because each stop costs two mode objects and a second rate would push a dense ladder past the roughly 400-object ceiling where `applySettings` rejects the whole set. The findings behind this recipe (mode declaration rules, the object ceiling, the required unmirror-before-destroy teardown order) live in `scripts/mirror-hidpi-probe.swift` and its commit history; `restore()` always unmirrors before destroying the virtual, since destroying the master of a live mirror is undefined. The feature is ultrawide-only (21:9 and wider) for now (`beyondCapStops`): a 16:9 4K or 5K panel is also capped (7680/10240 backings) and would grow the same stops, but is untested.

## VirtualDisplayService.create

`CGVirtualDisplay(descriptor:)` requires the main thread and returns nil off it, so descriptor build and init run on the main actor; only `apply(_:)`, which blocks on WindowServer IPC, runs off-main inside `CGHelpers.runWithTimeout`. The descriptor's `productID`/`serialNum` must be both unique per config (else a second virtual display collides with the first and WindowServer mirrors or rejects it) and stable across recreations, because macOS keys per-display settings, including the "what do you want to show" extend-or-mirror choice, on that identity; both halves are derived from the config's UUID so they never change. Size is computed from a fixed 110 PPI so each resolution reports a physical size like a real panel of that resolution, which makes macOS default to the native resolution instead of a scaled Retina mode (matching how BetterDisplay presents virtual displays); shrinking the reported size does not avoid the "what to show" prompt, since that prompt is gated on the display's reported type (HDMI/TV), not physical size, only on the default scaling. New-display registration pops that system picker, which steals key focus and would trip the panel's outside-click auto-dismiss, so `PanelOpenGuard.suppressAutoDismiss` is held for 1.5 s around creation. macOS auto-assigns a scaled looks-like-1080p default mode to any high-resolution virtual display no matter which modes are supplied, so `applyNativeResolution` retries briefly after creation until the native 1x mode (point size equals pixel size) sticks, or gives up.

## ResolutionService

Applying a mode is mirror-aware: when the target display is a mirror target, the mode must go to the mirror SOURCE (the virtual display) instead, because `CGConfigureDisplayWithDisplayMode` silently hangs or fails on a mirror target, whose mode is driven by its source. `setDisplayMode` first tries an exact `ioDisplayModeID` match, then, only on a mirror redirect (where the source has a different modeID space), a logical-size-plus-HiDPI match; for a normal display a missing ID means a CGS-injected hidden mode (e.g. a 144 Hz HiDPI-1080p variant) that must go through the CGS fallback instead, since size-matching there would wrongly pick CG's separate low-refresh twin. The CGS fallback (`cgsFallback`) applies a mode by its raw modeNumber via the private `CGSConfigureDisplayMode`, whose first argument is a CONFIG TOKEN from `CGBeginDisplayConfiguration`, not a connection id: passing the connection id segfaults in `checkCapacity()` on macOS 26, so it must run inside a real Begin/Complete transaction (verified against BetterDisplay on Tahoe). Sleep/wake restore (`restoreModeAfterWakeIfNeeded`, ticket w18z) matches by attributes (width, height, refresh within 1 Hz, HiDPI), never by the volatile `ioDisplayModeID`, because macOS reassigns that ID whenever the mode list is rebuilt (HiDPI override inject/remove, reconnect, sleep/wake), and matching by a stale ID resolved to a different, often off-aspect 60 Hz mode on wake. The sleep snapshot (`sleepModes`) lives for exactly one sleep, keyed by display UUID, and is cleared at every launch: the store it replaced remembered a mode chosen in Crisp forever, so a resolution picked with a monitor attached kept getting reapplied to the built-in at every later wake, overriding the mode macOS correctly keeps per display set. If the online display set differs from the one snapshotted (a display came or went while asleep) the restore is skipped rather than cleared, since the desk may still resolve to its old shape on a later wake pass.

## HiDPIService

The HiDPI override plist lives at `/Library/Displays/Contents/Resources/Overrides/DisplayVendorID-<vendor>/DisplayProductID-<product>` and needs a privileged write (AppleScript "with administrator privileges"), since that directory is root-owned on a stock Mac; `enableSmoothScaling` skips the privileged write, and its admin prompt, whenever the on-disk plist already carries exactly the wanted dense mode set, since reading `/Library/Displays` needs no privileges. The smooth-scaling ladder (`generateSmoothScaledModes`/`smoothScaledLogicalSizes`) steps the native width down by 16 points at a time (BetterDisplay's own step, which keeps the 2x backing an integer) down to a minimum scale, holding height to the panel's exact aspect ratio; a 1440p panel yields about 80 stops, dense enough for the slider to feel continuous, at the cost of flooding the System Settings resolution list, which is why it is opt-in per display. `smoothScalingSupported` is false on Macs whose GPU never renders a HiDPI backing larger than the panel (the A18 Pro in the MacBook Neo, issue #174): a 4K panel there only gets looks-like 1920x1080, and macOS refuses every size the dense ladder would add.
